# Public game APIs

These are native Netlify functions (`export default`, web `Request`/`Response`) in an ESM repository. Shared helpers live under `lib/`, outside the deployed function directory. Netlify's bundler includes the quiz passage JSON; no live storage or provider requests are needed to build or test.

## Configuration and limits

Set existing credentials in Netlify's Functions environment: `GEMINI_API_KEY` and/or `GROQ_API_KEY` for weapon generation and meaning scores; `GOOGLE_TRANSLATE_API_KEY` for Google Translate; optional `POLLINATIONSAI_API_KEY` for Wizard Brawl icons. Icons use the authenticated [Pollinations image API](https://gen.pollinations.ai/docs) (`gen.pollinations.ai/image/`, model `flux`); without an image key, or if generation fails, the game uses its procedural artwork. Never place keys in public Vite environment variables. Without a translation key the existing MyMemory fallback is used, subject to that provider's own quota. No credentials are required for local mocked tests.

Two deployed functions declare Netlify edge rate limits per IP and domain over 60 seconds: a shared allowance of 120 requests for the four AI routes, plus 60 quiz-stat requests. The AI gateway explicitly aliases the original translate, meaning-score, forge, and compile URLs, preserving existing game clients. Implementation modules live in `handlers/`. Keeping two rules supports Free, Starter, and Personal plans without assuming a paid account. The AI allowance leaves room for translation chains and retries. The limiter is shared across function instances by Netlify, not a process-local counter; preflight requests also count. The separately deployable Botanical Brawl subproject declares its own 12-per-minute forge rule.

These limits mitigate individual-client abuse; they are not a hard billing cap. [Netlify documents](https://docs.netlify.com/manage/security/secure-access-to-sites/rate-limiting/) an enforcement delay of up to 10 seconds, and domain-wide aggregation requires Enterprise with High-Performance Edge. Verify the rules appear on a deploy preview's **Rate limiting** page before publishing. Local tests check declarations; they cannot emulate or prove edge enforcement. Provider-side project quotas and budgets, current model availability, account configuration, and live credentials must be checked in the respective provider consoles. No claim is made that an allowlisted model is free on a particular account.

LLM calls have a 20-second total budget, 6 seconds per provider attempt (including response decoding), and at most four attempts. The exact allowlist is in `lib/llm.js`: two Gemini models followed by two Groq models. No model listing or arbitrary fallback is performed. When refreshing the allowlist, check [Google's official model catalog](https://ai.google.dev/gemini-api/docs/models) for stable model IDs and project-eligibility restrictions. Empty, blocked, truncated, malformed, or semantically invalid outputs do not count as success. Wizard Brawl may spend up to four additional seconds on optional icons; each icon is restricted to an expected image MIME type and 512 KB.

Translation also has a 20-second total deadline. Its 2,000-character input/output limit permits growth from the UI's 500-character starting prompt across language hops. MyMemory input is split at word boundaries where possible into at most 500 UTF-8 bytes per query, in batches of three concurrent requests, without silently truncating text. Failed provider status embedded in HTTP 200 responses is rejected.

APIs return JSON errors with `error` and `code`, using 400 for malformed input, 413 for oversized bodies, 415 for unsupported content types, 405 for unsupported methods, 409 for conflicting quiz replays, 502 for provider failure, 503 for unavailable configuration/storage, and 504 for expired deadlines. The edge returns 429 before invoking the function when its limit is enforced; that platform response is not generated by our JSON handler.

The Gemini defaults are `gemini-3.5-flash-lite` and `gemini-3.8-flash` because Google's [deprecation guidance](https://ai.google.dev/gemini-api/docs/deprecations) restricts 2.5 access to existing users; requests use the compatible `minimal`/`low` [thinking levels](https://ai.google.dev/gemini-api/docs/thinking) and recommended default sampling while retaining output caps and Groq's separate settings.

Groq uses `openai/gpt-oss-20b` and `openai/gpt-oss-120b`: its earlier Llama defaults were [retired for standard accounts on August 16, 2026](https://console.groq.com/docs/deprecations). Requests use the supported [low reasoning effort](https://console.groq.com/docs/reasoning), omit reasoning from responses, and use `max_completion_tokens` with 1,024 tokens of reasoning headroom above the requested output budget, capped at 8,192 total completion tokens. The existing deadlines and four-attempt ceiling still apply.

## Quiz statistics

The browser creates a UUID for each ten-answer game and sends the same UUID for any retry. The server requires ten distinct known passage IDs, validates guesses, and derives the score from the checked-in source labels. Client-provided correctness and confidence are never used for global aggregates. This prevents accidental or malformed score inflation; a public unauthenticated quiz cannot establish whether a human actually played or looked up its public answer key.

The existing `turing-shuffle-stats` store now uses immutable `games/v2/<uuid>` records, a persistent duplicate-check index, and 16 aggregate shards. The old `_global` and `_passages` keys remain an unchanged legacy baseline. Records previously written under `games/v1/` migrate without deletion. The SDK must support Blobs' documented atomic `onlyIfNew` and `onlyIfMatch` writes (the installed version is 11.1.0).

Each shard has one small manifest under `stats/v2/heads/` containing its aggregate totals, index-root reference, and unfinished legacy migration partitions. The index consists of immutable, content-addressed radix pages under `stats/v2/pages/`. A leaf holds at most 32 UUID/digest entries; an internal page references at most 16 children. Random UUIDs normally need only a few pages, and traversal is limited by the UUID's 32 hexadecimal digits. Pages are verified against their SHA-256 names when read. Counters, votes, record shapes, and migration frontiers are validated; invalid storage returns an explicit error.

To accept a submission, the handler first conditionally creates its immutable record. It then writes any new immutable index pages and conditionally publishes the manifest using the ETag it read. Membership, total score, passage votes, and migration progress change together in that single publication. If another writer won, the handler reloads the manifest and recomputes the change. There is no separate mutable-counter update that can be lost, and no multi-key transaction or rollback is assumed. A success response is sent only after membership and totals are published. The operation has a 10-second deadline and at most 24 conflict retries with jitter.

If a request fails after persisting its record but before manifest publication, its original UUID can be retried to finish the update. The game automatically retries network failures, 429, and 5xx responses up to three attempts within a 20-second overall budget, preserving the exact serialized payload. It respects Retry-After when it fits the budget and does not retry permanent 4xx responses. A lost response after publication is also safe: the existing index membership prevents a second contribution. An identical retry returns success; different answers with the same UUID return 409. A replay of a v1 UUID is checked against the old immutable record and uses the same membership index as migration, so racing replay and migration cannot count it twice. Original server scores remain attached to accepted records if passage labels later change. The earlier aggregate-only legacy scores cannot be revalidated. An unavailable aggregate shows a neutral unavailable message; only a confirmed zero-game response says to be the first to play.

After migration, a statistics GET performs exactly **18 strong-consistency reads**: one manifest for each of the 16 shards and the two original legacy aggregates. It does not list game records, traverse the index, or rewrite totals, so its work does not grow with lifetime games. Each shard is read consistently; games accepted during the GET may appear on either side of that shard's read. Netlify's CDN additionally caches successful responses for 30 seconds with up to 120 seconds of stale-while-revalidate freshness.

### One-time migration and recovery

The first statistics read records a migration start marker and waits 65 seconds before completing any v1 partition, allowing in-flight requests from the retired writer to drain. This exceeds Netlify's documented [60-second synchronous execution limit](https://docs.netlify.com/build/functions/configuration/). New submissions can be accepted during the wait. Only the current production deployment may write statistics after the transition; do not invoke old deployment URLs or run the old v1 writer concurrently after the drain window.

Migration then advances during GETs, with a 10-second deadline and limits of 512 record reads and 48 prefix partitions per invocation. Oversized partitions split into smaller UUID prefixes; the process never depends on key ordering, an undocumented listing cursor, or a full lifetime scan in one request. Each complete partition and its deduplicated contribution are persisted atomically in its shard manifest. A crash or deadline leaves completed work intact, while an incomplete partition is retried. Temporary `503 stats_rebuilding` responses continue until every shard finishes; partial totals are never presented as global totals. Repeated ordinary statistics reads finish the migration even when the old record set already exceeds 5,000 games.

Historical records, index pages, and legacy totals are retained. A failed manifest publication can leave unreachable immutable pages, which are harmless but consume storage. This removes the lifetime read cliff; it does not make storage or write contention unlimited. A future high-volume service should use a transactional database rather than increasing request work budgets or deleting index pages without a safe reachability/retention protocol.

Old open browser tabs without a UUID must reload to submit. Only Netlify's current published production deployment selects the original site-wide named store. Deploy previews, branch deploys, unpublished production deployments, and local development automatically use [deploy-scoped Blobs stores](https://docs.netlify.com/build/data-and-storage/netlify-blobs/#getdeploystore), selected from the native [deployment context](https://docs.netlify.com/build/functions/api/#deploy). Opening the quiz in a preview therefore cannot start production migration or write live scores. Those isolated stores retain the same one-time 65-second warmup. Do not direct synthetic GET or POST tests at the published production site: GET writes migration state while rebuilding. No production data was read, migrated, or written while implementing this change.

## Verification

`node --test tests/api-reliability.test.mjs tests/api-stats-compaction.test.mjs tests/api-stats-client.test.mjs tests/llm-compatibility.test.mjs tests/wizard-compile.test.mjs` runs mocked provider timeouts, validation, model fallback, Unicode translation, and the statistics scenarios above. It migrates 6,200 historical records, writes 5,104 new games, asserts constant GET storage calls, races same-shard writers and legacy replays against migration, and injects failures before and after record/page/manifest publication. It also checks the rollout drain, resumable timeouts, malformed storage, prototype-sensitive IDs, client retry identity/deadlines/Retry-After, unavailable UI copy, two deployed API rate-limit rules, model-specific request compatibility, safe Wizard text rendering, zero-valued weapon stats, and icon fallback/response bounds. No test invokes a paid provider or writes Netlify storage; all credential-bearing mocked requests use test values.

The storage design follows the official [Blobs API](https://docs.netlify.com/build/data-and-storage/netlify-blobs/) conditional-write contract and its recommendation to avoid transactional counters. Deploy preview validation should verify function routing/build metadata and benign method/input errors without calling providers or posting game results.
